# The Governance Interface: What This Module Is About

Every earlier module in this track has been about *doing* evaluation. Mod-101 built the statistical foundations. Mod-102 built the benchmark. Mod-103 taught classical metrics with slice discipline. Mods-104 through 109 built runners, judges, human panels, generative and agent-specific evaluations, and the safety and red-team disciplines. Mod-110 turned all of that into a production regression program. Mod-111 packaged the whole thing into an eval-as-a-service platform. The reader has, by this point in the track, the technical apparatus to run a defensible evaluation on almost any modern model.

This module is not about doing more evaluation. It is about the *interface* between the eval program and the four groups of people who do not do evaluation but who consume its outputs: the product team that ships the model, the regulator that audits the shipment, the leadership that funds the program, and the finance function that pays the bill. Each of those consumers asks a different kind of question of the eval program, and each expects an answer in an artifact shape that the eval program has to produce whether or not the eval engineers have practiced producing it. The failure modes at this altitude are almost never "the eval was wrong." They are "the eval was right and nobody could use it." Wrong eval + right artifact is a caught problem. Right eval + wrong artifact is an uncaught one.

Concretely: an eval program can be technically excellent and *still* fail to block a launch that should have been blocked because the release manager did not have a document that said "if this number is below X, do not ship." An eval program can produce state-of-the-art safety measurements and *still* be judged non-compliant with the EU AI Act because it did not produce a technical file structured the way Annex IV expects. An eval program can be objectively cheaper per-eval than any hosted alternative and *still* be defunded because its leaders never wrote down a defense of the cost/coverage trade-off in a form leadership recognized. This module is about producing the artifacts that convert engineering excellence into decisions the rest of the organization can defend.

## The five governance artifacts this module builds

The rest of the module is organized around five concrete deliverables. Each maps to one of the module's learning objectives, and each is an artifact you should be able to hand to a specific non-evaluator consumer.

- **The release-gate eval plan (Chapter 2)** — the document a product team, a release manager, and an incident owner all consume. It translates a product specification into a concrete list of gates, with pre-committed thresholds and pre-committed rollback triggers. The consumer is the release train; the failure mode it prevents is the gate that "was never a real gate."
- **The model card (Chapter 3)** — the document an internal review body and (increasingly) an external regulator consume. It compiles the evidence from the eval program into a structured description of what the model does, what it does not do, and where its measured limits are. The consumer is the reviewer, not the marketing team; the failure mode it prevents is the card that lists capabilities without listing measured limits.
- **The regulator crosswalk (Chapter 4)** — the document that maps the eval program's outputs to the frames the NIST AI RMF, ISO/IEC 25059, and the EU AI Act use. The consumer is the compliance function and, transitively, any regulator or auditor those functions have to answer to; the failure mode it prevents is the eval program that measured the right things under a different vocabulary and did not translate.
- **The platform decision dossier (Chapter 5)** — the document that explains why the organization is building parts of the eval platform in-house and buying parts of it from Arize Phoenix, Langfuse, W&B Weave, OpenAI evals, or a vendor-hosted alternative. The consumer is leadership; the failure mode it prevents is the "we should probably rebuild it ourselves" conversation that recurs every eighteen months without a resolvable decision on the table.
- **The budget defense (Chapter 6)** — the document that explains what the eval program spends on cost, wall-clock, and coverage, why the trade-off is where it is, and what would change if the constraint changed. The consumer is leadership again, plus finance; the failure mode it prevents is the annual budget review that terminates half the eval program because nobody documented what it was buying.

Each of the five is a *governance artifact* in the sense that it exists to let someone who is not an eval engineer make a decision that affects the eval program. Each is a discipline the reader will practice in this module's exercises.

## Why this altitude matters as an engineering discipline

There is a temptation, at this altitude, to treat these artifacts as documentation — the "PM writes the release plan; the compliance team writes the crosswalk; the CFO argues the budget." That is not the discipline this module teaches. In organizations where the eval program is not a first-class function, the artifacts either do not exist or exist without engineering rigor, and the eval engineers are then surprised when the release, the regulator, or the CFO make decisions the eval evidence did not support. The reader's job — the reason the artifacts are engineering artifacts and not documentation — is to build them from the ground truth of the eval evidence, keep them in sync with the eval program as it evolves, and defend them when they are questioned.

The engineering rigor at this altitude has three parts:

- **Traceability.** Every claim in every artifact traces to a concrete eval result in the mod-111 warehouse. A refusal rate on a model card traces to a specific run of a specific safety eval on a specific model revision. A gate threshold in a release plan traces to a specific bootstrap variance estimate from mod-101 on a specific incumbent's rolling history. A cost line in a budget defense traces to a specific per-workload-class row in the warehouse's cost attribution query. Untraceable claims are the failure mode the discipline exists to prevent.
- **Versioning.** Each artifact has a version and a change log. When the eval plan's threshold moves from 0.92 to 0.93, that is a versioned edit with a rationale. When the model card's safety section is updated because a new eval was added, that is a versioned edit with a rationale. Untracked edits are how governance artifacts become fiction over time — the release plan on the wiki says one thing, the release plan that actually blocks the deploy says another, and nobody notices until an incident.
- **A named audience.** Each artifact declares its audience — a specific person or role that reads it and makes a decision from it. An artifact whose audience is "everyone" is an artifact nobody actually reads. Chapters 2 through 6 each identify the audience explicitly.

The eval engineer's role at this altitude is closer to the SRE's role in a service-owner discipline than to the researcher's. The point is not that the release plan is beautifully written; the point is that when the release manager consults it, the plan tells them exactly what to do.

## Where this module sits relative to earlier modules

This module composes with, and does not replace, the earlier modules. Three seams deserve explicit disclaimers so the boundaries are clear.

- **Mod-101 through mod-109 provide the measurements.** The eval program at this altitude does not decide *what* to measure without doing the construct-validity, benchmark-engineering, and judge-calibration work those modules build. If the underlying evaluations are ill-formed, no governance artifact can rescue them; the artifacts inherit the validity of their inputs. When a chapter here says "the plan gates on refusal rate," it presupposes that mod-109 has been done well enough that refusal rate is a real measurement.
- **Mod-110 provides the operational altitude.** The release-gate plan of Chapter 2 is the artifact that sits behind the release-blocking gate mod-110 Chapter 2 taught the reader to design. The shadow, A/B, and continuous-monitoring altitudes of mod-110 Chapters 3 through 6 all consume the release-gate plan's post-launch clauses. Mod-112 does not re-derive those altitudes; it wires them into an artifact the rest of the organization can consume.
- **Mod-111 provides the substrate.** The results warehouse of mod-111 Chapter 5 is the source of truth every artifact in this module cites. The versioned registry of mod-111 Chapter 2 is where the datasets, judges, and prompts referenced in the model card and the regulator crosswalk live. If mod-111 is absent, the module's artifacts still work as documents but their claims are not traceable — the whole discipline erodes into narrative.

A reader who has skipped mod-111 can still learn the artifacts here, but the traceability discipline that makes them defensible depends on the substrate mod-111 built. In a mature organization, the two modules are inseparable.

## The three failure modes this module is written against

The chapters are structured, and the exercises are chosen, in explicit response to three failure modes that recur in organizations whose eval programs are technically good and governance-poor.

- **The invisible pass.** The eval program produces excellent measurements, but no artifact explicitly commits to "if the measurement is below X, do not ship." The result is a release culture that ships whichever candidate the training team most recently believes in, and the eval program becomes a research function whose reports are read after the fact. Chapter 2 is written against this failure mode.
- **The audit ambush.** The eval program produces excellent measurements, but they are structured against internal categories that do not line up with the regulator's categories. The compliance team asks for "Article 15 evidence" and the eval team produces a folder of dashboards that answers a different question. Chapter 4 is written against this failure mode.
- **The budget surprise.** The eval program produces excellent measurements at a cost that has been growing 30% quarter-over-quarter with no one signing off on the growth. In year three, leadership terminates half the program because the trade-off was never articulated in a form they could defend. Chapter 6 is written against this failure mode.

The other two chapters (Chapter 3 on model cards, Chapter 5 on build-vs-buy) are the disciplines that make the first three sustainable at scale — a model card is how the artifacts of Chapter 2 accumulate into a durable record; a platform decision dossier is how the trade-offs of Chapter 6 stay coherent as the program scales.

## What this module does not cover

Three adjacent topics are close enough that they deserve explicit disclaimers.

- **The rest of AI governance beyond the eval interface.** Model governance in the broadest sense — training-data provenance, red-team program governance, incident-response governance, policy authoring, board-level AI risk oversight — is a larger discipline than this module. This module covers the *eval interface* to that discipline. Where the eval program meets policy authoring, this module says "eval provides the evidence; policy authoring is out of scope."
- **The legal and regulatory analysis itself.** Chapter 4 walks the eval-program crosswalk to NIST AI RMF, ISO/IEC 25059, and the EU AI Act, but it is a crosswalk from the eval side; it is not a legal analysis of the regulations. The reader should treat Chapter 4 as the "translate your evidence into their vocabulary" discipline, not as an authoritative summary of the regulations themselves. Legal analysis lives with your organization's legal function, and the eval engineer's job is to hand them evidence in a shape they can use.
- **The org-design and hiring story.** How to build the eval team, how to structure the reporting line, how to price the role — those are real questions and this module does not answer them. The `JOB_REQUIREMENTS.md` file at the repo root is the closest artifact in this curriculum to a role definition; the org-design conversation is downstream of it and is out of scope here.

## Guidance for the reader working through this module

- **Practice with a real product, not a toy.** The exercises are structured so that a reader with access to a real (internal or open-source) product can apply them end-to-end. A toy product will let the reader mechanically produce the artifacts; a real product will make the trade-offs and the audience-fit decisions load-bearing, which is where the discipline lives.
- **Do not write the artifacts on top of vibes.** Every claim in every artifact should point at a specific eval result, a specific commit, or a specific external source. Vibes-based governance artifacts are the failure mode the module is written against.
- **Version the artifacts and store them alongside the code.** A release plan that lives on the wiki is a release plan that will be edited without provenance. A model card that lives in a `docs/` directory in the model repo is a model card that has a change history. Chapter 3 will be explicit about the "model card as code" discipline; the same principle applies to every artifact this module produces.
- **The artifacts compose.** The release-gate plan (Chapter 2) is one of the inputs to the model card's "measured limits" section (Chapter 3). The model card is one of the inputs to the regulator crosswalk (Chapter 4). The regulator crosswalk is one of the inputs to the build-vs-buy dossier (Chapter 5) — because "the platform we choose must let us produce this crosswalk cheaply" is a real requirement. Do not treat the five as five independent documents.

## Summary

This module is about the interface between the engineering discipline of evaluation and the four consumer groups — product, regulator, leadership, finance — whose decisions depend on eval outputs. It builds five governance artifacts: a release-gate eval plan, a model card, a regulator crosswalk to NIST AI RMF / ISO/IEC 25059 / EU AI Act, a platform build-vs-buy dossier, and a budget defense. Each artifact is an engineering artifact — traceable to warehouse-backed evidence, versioned, with a named audience — and each is written against a specific failure mode: the invisible pass, the audit ambush, the budget surprise, and the two disciplines that keep those failures from recurring at scale. The rest of the track produces the measurements; this module produces the artifacts that let the measurements do their governance job. The next chapter starts the sequence with the release-gate eval plan: the artifact that turns "we ran the evals" into "we are prepared to block the release when the evals fail."
