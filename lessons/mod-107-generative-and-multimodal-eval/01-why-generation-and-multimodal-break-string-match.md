# Why Generation and Multimodal Break String Match

The previous three modules — benchmark harnesses (mod-104), LLM-as-judge platforms (mod-105), human evaluation (mod-106) — gave you three ways to *score* a model output: a deterministic function against a reference (exact match, F1, ROUGE), a second model against a rubric, or a human against an annotation guide. This module is about the four families of task where those scorers *stop being interchangeable*, because the right thing to measure is not a string comparison at all.

- **Code generation.** The reference is not the answer. Two syntactically different programs can both be correct, and a program byte-identical to the reference can be wrong because a prompt-specified constraint was misread. The measurement that carries meaning is *did the program pass the tests I hold out*.
- **Math reasoning.** The reference is a single number or expression, but the model does not emit that number — it emits several paragraphs ending in the number, and the extraction step is doing more work than most authors acknowledge.
- **Retrieval-augmented generation (RAG).** There is a reference answer, but the interesting question is not "does the reply match" — it is "is the reply grounded in the retrieved context, and did the retriever retrieve the right context in the first place." Metrics have to peer inside the pipeline.
- **Multimodal.** The input is a pair (image, question) or (image, instruction). Reference-string equality applies only after the model has done the harder work of grounding the answer in pixels, and evaluation coverage becomes a question about *which slices of visual world* your suite touches.

The point of the module is not "generative eval is judge eval." It is that each of these four families has a specific measurement instrument the field has agreed on — pass@k for code, boxed-answer extraction plus process rubrics for math, faithfulness / relevancy / context precision-recall for RAG, VQA accuracy plus grounding-and-coverage discipline for multimodal — and running any of them without knowing the instrument's failure modes gets you a plausible number that lies to you in a specific way.

## The four families, in one sentence each

**Code generation** is a functional-correctness problem. The output is executable; therefore the metric can be behavioural. pass@k (Chen et al. 2021) is the ratio of problems where at least one of `k` samples passes a hidden test suite, estimated unbiasedly from `n ≥ k` samples per problem. It is the dominant metric because it does not care what the code looks like; it cares what the code *does*. That makes the underlying implementation — a sandbox to execute untrusted model output, a timeout policy that separates "wrong" from "slow," and a resource cap that keeps a malicious sample from taking down the eval host — the load-bearing part of the eval, not a plumbing detail.

**Math reasoning** looks like a QA task on the surface — GSM8K (Cobbe et al. 2021) and MATH (Hendrycks et al. 2021) each give you a problem and a single canonical answer. The metric is answer accuracy. The catch is that modern models emit long chains of thought, use `\boxed{}` (MATH's convention) or "the answer is 42" (GSM8K's convention) or JSON or a bare number, and any of those extractions can be brittle. A weak extractor can lose 5–15 points of measured accuracy on the same underlying reasoning, and different papers reporting different numbers on the same benchmark often disagree about extraction and normalization rules rather than about the model. The second layer of the eval — should the *process* be scored, not just the answer? — is why chain-of-thought rubrics enter the picture.

**RAG evaluation** does not fit a single-turn metric because the system under test is a *pipeline*: retriever plus generator, with the retrieved context as a hidden intermediate variable. RAGAS (Es et al. 2023) and TruLens (TruEra 2023) both instrument the pipeline with metrics that peer into that intermediate — faithfulness (does the answer stay inside the context), answer relevancy (does it address the question), context precision (are the retrieved passages relevant to the question), context recall (is the answer's supporting evidence in the retrieved passages). Each metric is a proxy, each metric has a known failure mode, and running them without knowing the failure modes tells you the pipeline is fine when it isn't.

**Multimodal evaluation** — vision–language tasks specifically — layers another degree of freedom onto everything above. VQAv2 (Goyal et al. 2017) and OK-VQA (Marino et al. 2019) score short-answer accuracy on images with human-annotated ground truth. MMMU (Yue et al. 2024) scores college-exam-style multi-image multi-domain reasoning. ChartQA (Masry et al. 2022) and DocVQA (Mathew et al. 2021) probe specific modality slices (chart understanding, document layout). CLIPScore (Hessel et al. 2021) scores caption alignment against reference-free image-text embeddings. None of these covers all of the visual world. A suite that runs only VQAv2 is not "measuring vision"; it is measuring "natural photos with short-answer VQA-style questions," and the model may still fail on a receipt, a scatterplot, or a satellite image. Coverage is a first-class eval-design question here, not a leaderboard-selection question.

## The instrument, not the number

Everything in this module is about the instrument. That is a deliberate contrast with the leaderboard-consumer view of these benchmarks: HumanEval pass@1 is a number, MATH accuracy is a number, RAGAS faithfulness is a number, MMMU accuracy is a number, and the model card puts them in a table. From the eval-engineer side each of those numbers is the output of a pipeline with named failure modes.

- pass@k needs a sandbox with a timeout and resource limits, or the "wrong" bucket silently accumulates infinite-loop and OOM samples. It also needs the *unbiased estimator* form when your sampling budget `n` differs from the `k` you report — the naive fraction is biased for `k < n` (Chen et al. 2021, §2).
- GSM8K accuracy needs an answer extractor that survives markdown, LaTeX, prose framing, and unit trailers. It also needs a decision about whether wrong-answer-right-reasoning counts, which is a *rubric* choice the number alone does not expose.
- RAGAS faithfulness reports "fraction of statements in the answer that are entailed by the context." It systematically misses omissions (the answer is faithful because it left out the wrong part), it inherits the entailment judge's biases, and its interpretation changes depending on whether the retrieved context is short or long. RAG metrics need an accompanying failure-modes section, or the number reads as "grounded" when it isn't.
- Multimodal accuracy on VQAv2 tells you approximately nothing about performance on tables in financial documents. Cross-modality generalization is not automatic; MMMU exists because VQAv2 pass rates saturated without models becoming actually competent on college-course-style multimodal reasoning.

The chapters walk each of these four instruments in turn, then close with the composition question: given the four instruments plus everything from mod-104 / mod-105 / mod-106, how do you assemble a suite for *your* product surface (a coding assistant, a spreadsheet copilot, a document-QA app, a visual search feature) that measures what shipping actually depends on — not what the model card table happens to list?

## The four objects, translated for generative and multimodal

The four-objects taxonomy from mod-104 Chapter 1 still applies. The vocabulary just shifts:

- **Model adapter.** For code and math, generation adapters — decoding parameters (temperature > 0 for pass@k sampling; typically temperature = 0 or greedy for math), stop tokens, max tokens tuned for chain-of-thought. For RAG, the adapter often wraps a *pipeline* (retriever + generator), not a single model. For multimodal, adapters must accept image inputs; provider APIs vary widely in what they accept (URL, base64, tokenized image tensor) and in per-image token budgets.
- **Task definition.** For code, a problem statement, function signature, and a hidden unit-test suite (the eval-engineer's part is the *test suite*, not the problem). For math, a problem statement and the reference numeric answer. For RAG, a question, an optional gold answer, and an optional gold context — RAGAS supports both reference-full and reference-free variants. For multimodal, a question and an image (or an image list); ground-truth answers are typically a list of human-provided alternatives against which the model's answer is scored.
- **Request type.** Generation, uniformly, on the subject side. Some RAG and multimodal metrics use a *judge* on the scoring side, inheriting all of mod-105's failure modes on top of the family-specific ones.
- **Scorer and aggregator.** This is where the families diverge sharpest and where most of this module's chapters live. Executor + timeout + pass@k estimator for code. Extractor + normalizer + accuracy for math. A per-metric judge chain plus a metric aggregator (RAGAS composite score, per-metric distribution, or a judge-panel majority) for RAG. Short-answer normalisation plus per-slice accuracy for multimodal VQA.

The reason the taxonomy still helps is that when a new benchmark or new tool shows up — LiveCodeBench, SWE-bench, GaiA, MMBench, whatever the next generation ships — you can read its README in an hour by mapping it onto these four slots and identifying which of its choices diverge from the harness you already use.

## What this module is not

- **Not a survey of every generative benchmark.** HumanEval, MBPP, LiveCodeBench, BigCodeBench, SWE-bench, GSM8K, MATH, MathVista, HotpotQA, HELM RAG scenarios, RAGAS, TruLens, VQAv2, OK-VQA, MMMU, MMBench, ChartQA, DocVQA, CLIPScore — mentioning them all does not teach any of them. The chapters teach the *instruments* (pass@k, extraction + CoT rubric, RAGAS metric family, VQA accuracy + coverage) and use the canonical benchmark for each as the concrete instance. Newer benchmarks slot into the same instrument.
- **Not a judge tutorial.** RAGAS, TruLens, and many multimodal graders are judge-based under the hood, but the judge machinery — rubric anchoring, bias controls, calibration — is already in mod-105. Here we import it and focus on the family-specific measurement.
- **Not a leaderboard-hunting exercise.** The final chapter and final exercise are deliberately about *not* running a leaderboard collage. If your product is a Python coding assistant for internal data-engineering teams, the eval suite is not "MMLU + HumanEval + MMMU + HellaSwag" — it is a defensible slice of pass@k on tasks that look like your users' notebooks, plus a documented gap where you know you're under-measured.

## Summary

Four families of task — code generation, math reasoning, retrieval-augmented generation, and multimodal — cannot be scored well by string-match or by a generic judge alone. Each has a canonical measurement instrument the field has agreed on: pass@k with sandboxed execution for code, extraction plus optional chain-of-thought rubrics for math, RAGAS/TruLens metrics (faithfulness, answer relevancy, context precision/recall) for RAG, and VQA-style short-answer accuracy plus explicit modality-coverage discipline for multimodal. Each instrument has documented failure modes that reduce the reported number to noise if you run the instrument without them. The remaining chapters walk each instrument in turn, then close with how to compose a suite that maps a real product surface to a defensible mix of these instruments, rather than to whatever appears on the current model-card table.
